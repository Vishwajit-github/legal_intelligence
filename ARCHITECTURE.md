# Legal Intelligence Multi-Agent AI System Architecture

## 1. System Overview

This project implements a legal-focused multi-agent AI orchestration platform built with:

- FastAPI
- LangGraph
- LangChain agents and tools
- OpenAI-compatible LLM APIs
- Chroma vector retrieval for internal UAE legal content
- PDF extraction, OCR fallback, embeddings, and FAISS retrieval
- JSONL logging and trace collection

The system accepts legal questions with optional uploaded legal documents. It routes each request through a supervisor-led workflow where specialist legal agents perform research, clause extraction, contract review, compliance review, risk analysis, litigation analysis, summarization, or drafting. A validator node checks the output before the API returns the final response.

The system is designed for legal intelligence and drafting assistance only. It does not provide legal advice and should not replace qualified legal counsel.

## 2. High-Level Architecture

```text
User Request
    |
    v
FastAPI API Layer
    |
    v
LangGraph Workflow
    |
    v
Supervisor Node
    |
    v
Legal Supervisor Agent
    |
    +--> Legal Research Agent
    +--> Legal Clause Extraction Agent
    +--> Contract Analysis Agent
    +--> Legal Compliance Agent
    +--> Litigation Strategy Agent
    +--> Legal Summarization Agent
    +--> Document Drafting Agent
    +--> Legal Risk Assessment Agent
    |
    v
Validator Node
    |
    +--> END
    +--> Retry Supervisor
```

The architecture is intentionally supervisor-centered. The API does not directly choose a specialist. It prepares the state and lets the supervisor decide which legal specialist tools are required.

## 3. Runtime Entry Points

```text
run.py
    Starts the FastAPI app through Uvicorn on port 8000.

app.py
    Defines API endpoints, handles uploads, builds initial graph state,
    invokes the LangGraph workflow, and returns structured API responses.

graph/builder.py
    Compiles the LangGraph workflow with supervisor, validator, and router.

graph/nodes/supervisor_node.py
    Invokes the Legal Supervisor Agent, collects agent traces,
    writes chat history, and updates graph state.

graph/nodes/validator_node.py
    Uses the legal validator prompt to validate supervisor output.

graph/nodes/router.py
    Routes to END or retries the supervisor based on validation state.

config/llm.py
    Loads .env.example and initializes the shared chat model,
    embeddings client, and raw OpenAI-compatible client.
```

## 4. API Layer

The FastAPI app is defined in `app.py`.

### Health Endpoints

- `GET /`: returns a basic running message.
- `GET /health`: returns health status.

### Main Endpoints

- `POST /run`: main legal analysis endpoint.
- `POST /legal/debug`: debug endpoint that returns the full graph output.
- `GET /history/{run_id}`: returns stored chat history for a session.

### Request Inputs

`POST /run` accepts multipart form input:

- `user_query`: required legal query.
- `run_id`: optional session identifier.
- `file`: optional uploaded document.

Uploaded files are stored under `uploads/`. The API detects file type by extension and adds file metadata into the graph state.

## 5. Graph State

The workflow state is built in `app.py` and passed into the schema declared in `graph/state.py`.

Important runtime state fields:

- `run_id`: session and trace identifier.
- `user_query`: original user legal query.
- `messages`: active conversation messages passed to agents.
- `uploaded_file_path`: file path generated by `app.py` for uploaded files.
- `uploaded_file_type`: detected file category such as PDF, Word, text, or image.
- `uploaded_file_mime_type`: original upload MIME type.
- `supervisor_output`: raw supervisor response.
- `validation_result`: parsed validator JSON.
- `validation_risk_level`: low, moderate, high, or unknown.
- `is_valid`: validation pass/fail flag.
- `iteration`: retry counter.
- `used_agents`: agent usage tracking.
- `agent_outputs`: collected specialist agent traces.
- `final_response`: response returned to the user.
- `chat_history`: recent stored session messages.

Implementation note: the state class is still named `HealthcareState`, and upload field names in the typed schema are not fully aligned with the runtime fields initialized by `app.py`. The active workflow still carries the runtime keys through the graph, but the schema should be renamed and cleaned up in a follow-up pass.

## 6. LangGraph Workflow

The active graph has two executable nodes and one conditional router.

```text
START
  |
  v
supervisor
  |
  v
validator
  |
  +-- if valid --------------------> END
  |
  +-- if iteration >= 3 -----------> END
  |
  +-- if retry_allowed is false ---> END
  |
  +-- otherwise -------------------> supervisor
```

Graph behavior:

- The supervisor always runs first.
- The validator always reviews supervisor output.
- Valid output ends the run immediately.
- Invalid output can be retried until iteration `3`.
- Validator output can block retry by setting `retry_allowed` to `false`.
- The API returns the final state after graph completion.

## 7. Supervisor Layer

The supervisor layer has two parts:

- `graph/nodes/supervisor_node.py`: graph node wrapper.
- `src/agents/supervisor_agent.py`: LangChain agent with specialist tools.

The supervisor node:

1. Ensures a `run_id` exists.
2. Initializes trace context.
3. Loads recent chat history.
4. Merges history with current messages.
5. Invokes `supervisor_agent`.
6. Extracts the final AI message.
7. Collects specialist traces from `CURRENT_TRACE`.
8. Writes agent output events to `logs/legal_agent_trace.jsonl`.
9. Appends user and assistant messages to chat history.
10. Updates graph state for the validator.

The supervisor agent itself is a routing agent. Its prompt tells it to select the appropriate specialist agents and avoid doing specialist legal analysis directly.

## 9. Prompt Architecture

Active prompts live in `prompts/`.

### Supervisor Prompt

Defined in `prompts/__init__.py` as `LEGAL_SUPERVISOR_PROMPT`.

Responsibilities:

- identify user intent
- choose correct specialist agents
- prevent the supervisor from doing legal work directly
- preserve specialist output
- limit final synthesis
- enforce one-tool-use-per-request expectations

### Specialist Prompts

Defined in `prompts/__init__.py`.

Each specialist prompt defines:

- role and boundaries
- when to use tools
- prohibited behavior
- expected output style
- grounding and uncertainty rules

### Validator Prompt

Defined in `prompts/validator_prompt.py` as `VALIDATOR_PROMPT`.

The validator checks:

- relevance to the legal question
- support from available evidence
- legal reasonableness
- safety and non-misleading framing
- completeness
- hallucinated laws, citations, clauses, or obligations

The validator must return valid JSON:

```json
{
  "is_valid": true,
  "risk_level": "low|moderate|high",
  "reason": "...",
  "fix_needed": "...",
  "retry_allowed": true
}
```

Legacy note: `prompts/planner_prompt.py` and `prompts/critique_prompt.py` still contain healthcare prompt scaffolding and are not part of the active Legal AI graph.

## 10. Tool Architecture

Tools live in `src/tools/`.

### Internal Legal Research Retrieval

File: `src/tools/legal_research_tool.py`

Tool:

- `legal_research_retrieval_tool`

Behavior:

- loads Chroma from `data/vector_dbs/uae_legal_compliance_vector`
- embeds the user query
- returns top semantic matches with source metadata
- supports UAE legal and compliance research

### Contract Document Retrieval

File: `src/tools/legal_document_retrieval_tool.py`

Tool:

- `contract_document_retrieval_tool`

Behavior:

- opens uploaded PDF with PyMuPDF
- detects whether the document is structured or unstructured
- uses LLM OCR fallback when text extraction is weak or the document is unstructured
- returns full text for smaller documents
- chunks larger documents
- embeds chunks
- builds an in-memory FAISS index
- returns top relevant chunks

### Clause Extraction

File: `src/tools/legal_clause_extraction_tool.py`

Tool:

- `legal_clause_extraction_tool`

Behavior:

- extracts PDF text
- detects clause or article numbers from user query
- performs exact numeric matching where possible
- falls back to semantic retrieval
- deduplicates matched and retrieved chunks
- returns exact or relevant clause content

### Contract Summarization

File: `src/tools/contract_summarizer_tool.py`

Tool:

- `summarize_contract_document`

Behavior:

- extracts uploaded PDF content
- uses OCR fallback when needed
- returns full document text for smaller documents
- returns retrieved chunks for larger documents
- supports summary generation by the summarization agent

### Web Search Helper

File: `src/tools/web_search_engine.py`

Tool:

- `web_search_tool`

Behavior:

- uses the configured LLM to produce web-search-style legal or regulatory research output
- intended for external jurisdiction, recent-update, or supplemental legal context

Implementation note: this tool is currently LLM-backed and does not call a browser or external search API directly.

## 11. Document Processing Architecture

The document-processing path is designed mainly for legal PDFs.

```text
Uploaded File
    |
    v
uploads/<uuid>_<filename>
    |
    v
Specialist Agent Tool
    |
    v
PyMuPDF Text Extraction
    |
    +--> If weak text or unstructured PDF: LLM OCR fallback
    |
    v
Token Count
    |
    +--> Small document: return full text
    |
    +--> Large document:
           chunk text
           embed chunks
           build FAISS index
           retrieve top chunks
           return relevant context
```

API-level file detection supports PDF, Word, text, and image extensions, but the active legal document tools are strongest for PDFs. Word and text support should be completed before production use.

## 12. Validation And Retry Architecture

The validator is intentionally separate from the supervisor and specialists.

Validation inputs:

- `user_query`
- `supervisor_output`
- `agent_outputs`

Validation output:

- `is_valid`
- `risk_level`
- `reason`
- `fix_needed`
- `retry_allowed`

Routing rules:

- If `is_valid` is true, end the run.
- If `iteration >= 3`, end the run.
- If `retry_allowed` is false, end the run.
- Otherwise, retry the supervisor.

This creates a lightweight quality-control loop without turning the validator into a second legal analyst.

## 13. Session Memory And Persistence

The system uses `run_id` for session continuity.

Stored chat history:

- file: `logs/chat_history.jsonl`
- writer: `append_chat_history`
- reader: `get_chat_history`

At request time:

1. The API loads recent history for the provided `run_id`.
2. The supervisor node also loads recent history.
3. Current user messages are merged with history.
4. Final assistant output is appended to history.

This gives follow-up questions access to recent context without a database dependency.

## 14. Observability And Tracing

Logging and tracing are implemented through:

- `src/utils/logger.py`
- `src/utils/agent_trace.py`
- `src/utils/trace_context.py`

Important log files:

- `logs/legal_agent_trace.jsonl`
- `logs/chat_history.jsonl`

Trace events include:

- node start
- node end
- specialist agent output
- router decision
- exception details
- validation output
- latency

The supervisor reconstructs `agent_outputs` from the in-memory `CURRENT_TRACE` object and also writes agent output events to the log file.

## 15. Runtime Configuration

`config/llm.py` loads environment variables from `.env.example`.
Do not commit real credentials in this file if the repository will be public.

Important variables:

```bash
OPENAI_API_KEY=your-api-key-here
OPENAI_BASE_URL=https://api.core42.ai/v1
OPENAI_MODEL=gpt-5.4
OPENAI_EMBEDDING_MODEL=text-embedding-3-large
```

Runtime clients:

- `model`: primary `ChatOpenAI` model.
- `llm`: alias for the primary model.
- `concise_response_llm`: lower token response model wrapper.
- `embeddings`: `OpenAIEmbeddings` client.
- `openai_client`: raw OpenAI-compatible client for OCR and embedding calls.

The client uses `truststore` for TLS verification.

## 16. Safety And Boundary Architecture

The safety model is prompt-based and validation-based.

Agent-level boundaries:

- no definitive legal advice
- no guaranteed legal outcomes
- no fabricated laws, regulations, cases, citations, clauses, or evidence
- no compliance certification
- no unsupported enforceability claims
- state missing information and assumptions clearly

Supervisor boundaries:

- route to specialists rather than performing analysis directly
- preserve specialist outputs
- keep final synthesis concise
- avoid adding new reasoning outside specialist results

Validator boundaries:

- fail fabricated legal authorities or unsupported legal conclusions
- pass legally reasonable, grounded, useful responses
- allow drafting output unless it contains major errors or fabricated references
- trigger retry only when needed

## 20. Architecture Summary

Legal Intelligence AI is a FastAPI and LangGraph-based multi-agent system. The API prepares request state, the supervisor chooses legal specialist agents, tools provide document and legal retrieval, the validator checks response quality, and logs preserve traceability. The current architecture is functional for local legal intelligence workflows, with a small set of legacy healthcare names and submission-readiness gaps still requiring cleanup.
